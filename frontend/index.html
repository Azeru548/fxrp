The product

A payment link that speaks dollars and settles the interoperable asset.

XRP is one of the largest assets without native smart contracts. FXRP, the FAsset on Flare, brings it into EVM DeFi — but merchants still cannot invoice a stable USD amount and get paid in that asset. Rowan is that missing rail.

Price in USD, convert on-chain

Merchants write invoices in cents — $20.00, $49.99 — the amount customers already understand. At payment time the contract reads Flare FTSOv2’s XRP/USD feed and computes the FXRP due, ceiling-rounded so the merchant never receives less than the stated dollar value. There is no off-chain FX desk and no trusted price API.

Shareable payment links

Every invoice is a URL: #/pay?c=<contract>&id=<n>. Drop it in checkout, email, or a QR code. The payer lands with the invoice pre-loaded.

No custodian

Collected FXRP sits in the FxrpPay contract. Only the invoice payee can withdraw. Rowan never holds keys, never runs a matching engine, never takes a cut.

Fixed FXRP invoices too

Need an exact token amount instead of dollars? Price the invoice in FXRP units. No oracle fee, same pay and withdraw flow.

Typed TypeScript SDK

@rowan/fxrp-pay-sdk wraps create, pay, withdraw, auto-approval, oracle fees, and link helpers. ESM + CJS, ethers v6.

Portable bytecode

One constructor argument — the FTSOv2 address — ports the same contract from Coston2 to Songbird and Flare Mainnet.

How it works

Three calls. The whole product.

Rowan is not a hosted checkout. It is a public contract and a static app. Anyone can create an invoice, anyone can pay it, and only the merchant can pull the settled FXRP.

01

Create

The merchant calls createInvoice with a payee, the FXRP token, a pricing mode (USD cents or fixed units), an amount, and an optional memo. The contract returns an id. Rowan turns that into a payment link.

02

Pay

The payer opens the link, connects any EIP-6963 wallet, and approves the token. pay(id) pulls the exact remaining due. USD invoices fetch FTSOv2 in the same transaction and refund leftover FLR.

03

Withdraw

Settled tokens sit in FxrpPay until the payee calls withdraw(id). The invoice auto-closes when fully paid. The payee can also cancel an open invoice if it should no longer accept funds.

Who it’s for

Built for people who already hold XRP or FXRP.

Merchants

Invoice a customer in dollars without running a processor, trusting a custodian, or converting off-chain. Share a link. Withdraw when the invoice closes. Payee is an address you control.

XRP / FXRP holders

Spend the interoperable asset against a USD price. You keep an EVM wallet on Flare, approve FXRP, and pay the exact due — the rate is the same feed anyone can read on-chain.

App builders

Drop the payment link into a checkout, or call the SDK from a React app or a Node backend. Reads work against the public Coston2 RPC with no wallet at all.

Hackathon & pilots

Remix-friendly Solidity, no imports, a static frontend, and live Coston2 evidence. The same contract is the production path once real FXRP is wired on Songbird or Mainnet.

Why Flare

XRP, spendable in EVM DeFi.

Flare is the only place this product is honest. FAssets wrap XRP as FXRP so it can move through ERC-20 rails. FTSOv2 publishes XRP/USD on-chain, so a dollar invoice does not need a trusted server to decide how much FXRP is due.

Rowan uses both primitives in the payment path itself — not as a badge. pay() calls getFeedByIdInWei(XRP/USD), pays the oracle fee in FLR, and refunds any excess atomically before pulling tokens.

The contract is a single Solidity file (0.8.20+, zero imports) so it compiles in Remix. Deploy it with the FTSOv2 address for the target network. USD mode requires that oracle; fixed-FXRP mode works even if the oracle is unset.

For developers

Ship a payment rail without a backend.

The typed SDK wraps the contract so a checkout can create an invoice, hand the payer a link, and later verify settlement from any Node process.

// merchant — $49.99 invoice, get a shareable link import { FxrpPayClient, PRICING_USD } from "@rowan/fxrp-pay-sdk"; const client = await FxrpPayClient.fromBrowserProvider(window.ethereum); const { id, link } = await client.createInvoice({ pricing: PRICING_USD, amount: "4999", memo: "Order #1234", }); // link → #/pay?c=0x29A6…&id=7

Link format #/pay?c=<FxrpPay>&id=<id>. Full method tables, types, pricing math, and examples live in the developer documentation.

FAQ

Straight answers.

Is this paying with native XRP on the XRPL?

No. The payer spends FXRP, the FAsset-wrapped XRP on Flare, from an EVM wallet. Native XRPL payment (mint FXRP from XRP in one flow) is on the roadmap via Flare Smart Accounts.

Where does the USD price come from?

Flare FTSOv2’s XRP/USD feed, read on-chain inside pay(). The frontend can preview the same math, but the contract is the source of truth. Conversions ceiling-round so the merchant is not shorted by a fraction of a token.

Who holds the funds?

The FxrpPay contract. Rowan has no operator key. Only the invoice’s payee address can withdraw collected tokens. Cancel stops new payments; it does not move funds.

What do I need to try the demo?

An EVM wallet (MetaMask, Rabby, and others via EIP-6963), Flare Testnet Coston2 (chain 114), free C2FLR from the Flare faucet, and test FXRP minted from the MockFXRP contract. Addresses are pre-filled in the app.

Are there protocol fees?

Rowan takes none. USD invoices may pay an FTSOv2 oracle fee in FLR (currently 0 on Coston2 for this feed). You still pay ordinary gas.

Can I use this in my own app today?

Yes, against the Coston2 deployment. Install the in-repo SDK (sdk/) or call the contract directly. See the SDK documentation for install, types, and examples. Mainnet requires a new deploy with real FXRP.
